# 0. Codex용 필독 요약

Codex는 구현 전에 이 절을 우선 기준으로 삼는다.

## 0.1 확정된 핵심 규칙

1. 게임은 **제어실 감시 모드**와 **현장 이동 모드**를 오간다.
2. CCTV 영상은 2D 횡스크롤 공간이며 플레이어는 화면을 좌우로 탐색한다.
3. 이상현상 보고 양식은 기본적으로 **[구역] + [대상] + [이상 유형]** 세 블록이다.
4. `관찰 유지`나 `처리 방식`은 보고 블록에 포함하지 않는다.
5. 정확한 보고가 제출되면 해당 CCTV에 노이즈가 발생하고, 노이즈 뒤에 정상 배치로 복원된다.
6. 잘못된 보고에는 성공 노이즈를 절대 사용하지 않는다.
7. 일반 이상현상은 보고로 정상화된다.
8. 정전, 서버 장애, 방화문 개방과 같은 긴급 사건은 보고만으로 해결되지 않으며 현장 이동을 요구한다.
9. 현장 이동 중에는 일반 이상현상의 미발견 타이머를 정지한다.
10. 한 근무일에 이상현상을 기본 3개 놓치면 게임오버다.
11. 미발견은 단순 점수 차감이 아니라 현상이 다른 구역 또는 제어실 쪽으로 접근하는 서사·공포 상태다.
12. 게임의 핵심 공포는 지속적인 추격이 아니라 **관찰하지 않은 곳에서 무언가가 가까워진다는 확신**이다.

## 0.2 구현 시 추측 금지 항목

- 엔진이 아직 고정되지 않았으므로 Unity, Godot, Unreal 전용 API를 핵심 도메인 로직에 직접 결합하지 않는다.
- 이상현상을 씬에 하드코딩하지 않는다. 가능한 모든 콘텐츠는 데이터 자산 또는 JSON 등으로 정의한다.
- 카메라별 정상 상태를 수작업 if문으로 복원하지 않는다. 기준 상태 스냅샷 또는 상태 프로필을 사용한다.
- 보고 성공 여부를 UI 문구만으로 처리하지 않는다. 도메인 이벤트를 발생시켜 시각·사운드·평가 시스템이 구독하게 한다.
- 플레이어가 현장에 있는 동안 백그라운드에서 일반 이상현상을 실패 처리하지 않는다.
- 무작위 이벤트는 플레이어가 판별할 수 없는 중첩을 만들지 않도록 스케줄러가 상호 배제 규칙을 적용해야 한다.

## 0.3 구현 우선순위

1. CCTV 화면 이동 및 채널 전환
2. 정상 상태 스냅샷
3. 데이터 기반 이상현상 생성
4. 블록형 보고 UI 및 판정
5. 성공 노이즈와 정상화
6. 미발견 누적 및 접근 연출
7. 일차 종료 평가
8. 정전 현장 이벤트와 복귀
9. 저장·불러오기
10. 콘텐츠 확장 도구

# 1. 제품 비전

## 1.1 플레이어 판타지

플레이어는 폐쇄 예정인 지하 의료시설의 야간 감시원이다. 제어실 안에서는 여러 CCTV를 전환하며 시설을 통제하는 듯한 우월감을 느끼지만, 실제로는 제한된 화면과 불완전한 기록에 의존한다.

플레이어가 느껴야 하는 감정의 흐름은 다음과 같다.

1. **학습:** 정상 배치를 외운다.
2. **의심:** 무언가 달라진 것 같지만 확신할 수 없다.
3. **판단:** 구역·대상·이상 유형을 선택해 보고한다.
4. **안도:** 정확한 보고 뒤 노이즈가 끼고 정상 상태가 복구된다.
5. **불안:** 다른 구역을 확인하지 못한 시간이 길어질수록 위험을 느낀다.
6. **노출:** 긴급 사건으로 제어실을 떠나 CCTV로 보던 공간을 직접 걷는다.
7. **불신:** CCTV와 현실이 일치하지 않는다는 사실을 체감한다.
8. **책임:** 놓친 현상이 제어실에 가까워지는 결과를 목격한다.

## 1.2 핵심 차별점

- CCTV 감시와 실제 횡스크롤 이동이 동일한 시설 공간에서 연결된다.
- 보고 성공 시 단순 체크 표시가 아니라 현실이 강제로 정상화되는 연출이 발생한다.
- 미발견 수치가 UI 숫자만이 아니라 소리, 그림자, 카메라 추가, 제어실 침입으로 시각화된다.
- 횡스크롤의 화면 끝과 뒤쪽 공간을 핵심 공포 장치로 사용한다.
- 복잡한 전투나 AI 없이도 데이터 기반 이상현상과 사운드로 콘텐츠를 확장한다.

## 1.3 디자인 기둥

| 기둥 | 설명 | 구현 판단 기준 |
|---|---|---|
| 관찰의 긴장 | 정상 상태를 기억하고 작은 변화를 탐지한다. | 변화는 공정하게 발견 가능해야 한다. |
| 기록의 책임 | 플레이어가 관찰 사실을 블록으로 분류한다. | 보고는 짧지만 의미 있는 판단이어야 한다. |
| 안전지대의 붕괴 | 제어실이 점점 안전하지 않게 느껴진다. | 미발견 결과가 제어실 주변에 축적되어야 한다. |
| 화면 밖 공포 | 보이지 않는 좌우 공간과 지나온 길을 활용한다. | 괴물 노출보다 소리·빛·실루엣을 우선한다. |
| 제한된 제작 범위 | 1인 개발로 완성 가능한 구조를 유지한다. | 시스템 재사용과 데이터 기반 확장을 우선한다. |

# 2. 목표와 비목표

## 2.1 제품 목표

- 15분 프로토타입만으로도 “제어실 밖에 나가기 싫다”는 감정을 만든다.
- 이상현상을 발견하고 보고하는 과정이 단순 클릭이 아니라 기억·분류 퍼즐이 되게 한다.
- 같은 배경을 반복 사용하더라도 상태 변화와 사운드로 콘텐츠 다양성을 확보한다.
- 일반 이상현상, 연쇄 이상현상, 긴급 현장 사건을 하나의 통합 데이터 구조로 관리한다.
- 실패 시 플레이어가 억울함보다 “내가 놓쳤다”는 납득을 느끼게 한다.
- 스트리밍에서 반응이 나오는 명확한 순간을 만든다: 노이즈 정상화, 제어실 접근, 현장 귀환, 복제 인물.

## 2.2 비목표

초기 제품에서는 다음을 구현하지 않는다.

- 전투, 무기, 체력 전투 시스템
- 자유 로밍형 대형 맵
- 복잡한 길찾기 AI
- 온라인 멀티플레이
- 절차 생성 맵
- 랜덤 조합만으로 구성되는 무한 모드
- 자유 텍스트 입력 보고서
- 모든 오브젝트와 상호작용하는 물리 샌드박스
- 풀 보이스 연기
- 장비 제작, 파밍, 성장 트리
- 반복적인 장거리 추격

# 3. 세계관과 내러티브

## 3.1 배경

시설은 과거 수면 장애, 기억 장애, 인지 동기화를 연구하던 지하 의료기관이다. 폐쇄 전 마지막 안전 점검을 위해 야간 감시 업무가 유지되고 있다.

공식 설명은 단순한 시설 상태 기록이지만 실제 업무 목적은 다르다.

> 시설의 이상현상은 관찰되지 않을 때 이동하고, 정확하게 기록될 때 현재 상태가 고정된 뒤 기준 상태로 교정된다.

플레이어가 제출하는 기록은 보고서가 아니라 일종의 현실 교정 명령이다.

## 3.2 서사 전달 방식

스토리는 긴 컷신보다 다음 수단으로 전달한다.

- 일차 시작 업무 공지
- 이전 감시원의 기록
- 정상 배치와 이상현상의 관계
- CCTV 시간과 실제 시각의 불일치
- 현장에서 발견되는 짧은 메모
- 시스템 데이터에서 사라지는 플레이어 이름
- 일차 평가 문서의 기계적인 문장 변화

## 3.3 정보 공개 단계

| 구간 | 플레이어가 믿는 사실 | 실제로 드러나는 사실 |
|---|---|---|
| 초반 | 단순 시설 이상을 보고한다. | 보고가 현상을 제거한다. |
| 중반 | 이상현상이 시설을 돌아다닌다. | 미발견 현상이 제어실로 접근한다. |
| 후반 | CCTV가 현실을 보여준다. | CCTV와 기록이 현실을 재구성한다. |
| 최종 | 플레이어는 감시자다. | 플레이어 자신도 관찰 대상일 수 있다. |

## 3.4 엔딩 방향

- **근무 완료:** 높은 정확도로 근무를 마치지만 새로운 감시원이 동일한 제어실에 앉는다.
- **기록자 교체:** 플레이어가 직원 목록에서 삭제되고 다음 감시원에게 이상현상으로 보고된다.
- **완전 봉쇄:** 시설 전원과 기록 서버를 파괴하지만 암전된 모니터에서 전환음이 계속 들린다.
- **관찰 대상:** 플레이어가 CCTV 속 자신을 보고하고 실제 제어실에서 사라진다.

MVP에는 2개 엔딩만 구현한다.

# 4. 전체 게임 구조

## 4.1 게임 단위

- 전체 게임: 여러 근무일로 구성
- 근무일: 준비, 감시, 긴급 사건, 종료 평가
- 감시 세션: CCTV 관찰과 보고가 반복되는 핵심 구간
- 현장 사건: 감시 세션을 중단하고 실제 시설로 이동하는 제한된 구간

## 4.2 전체 흐름

```text
타이틀
→ 새 게임 / 이어하기
→ 일차 브리핑
→ 정상 상태 확인
→ CCTV 감시
→ 이상현상 보고 및 정상화
→ 미발견 접근 연출
→ 긴급 사건 발생 시 현장 이동
→ 제어실 복귀
→ 근무 종료
→ 평가 및 서사 문서
→ 다음 일차
→ 최종 선택과 엔딩
```

## 4.3 근무일 상태 머신

```text
DayLoading
→ Briefing
→ BaselineReview
→ Monitoring
↔ Reporting
→ FieldDispatch (조건부)
→ FieldResolution
→ Monitoring
→ DayClosing
→ Evaluation
→ DayComplete 또는 GameOver
```

## 4.4 핵심 플레이 루프

```text
CCTV 채널 선택
→ 화면 좌우 탐색
→ 정상 상태와 비교
→ 이상현상 의심
→ 필요 시 최근 영상 재생
→ [구역] [대상] [이상 유형] 제출
→ 정확하면 노이즈 후 정상화
→ 틀리면 현상 유지
→ 다른 채널로 이동
```

# 5. 게임 모드

## 5.1 제어실 감시 모드

플레이어는 컴퓨터에 앉아 CCTV를 조작한다.

가능한 행동:

- CCTV 채널 전환
- 화면 좌우 스크롤
- 제한적 확대
- 최근 영상 다시 보기
- 기록 패널 열기
- 일차 정보 확인
- 긴급 사건 승인 후 자리에서 일어나기

불가능한 행동:

- 제어실 내부 자유 이동
- 정상 감시 중 임의로 현장 출동
- CCTV 화면 속 오브젝트 직접 클릭 처리

## 5.2 현장 이동 모드

플레이어 캐릭터를 횡스크롤로 직접 조작한다.

가능한 행동:

- 좌우 이동
- 제한된 조사
- 지정 장치 조작
- 문 사용
- 짧은 우회로 탐색

불가능한 행동:

- 전투
- 자유 인벤토리 조합
- 모든 방 진입
- 일반 감시 보고

## 5.3 평가 모드

근무 종료 후 다음을 표시한다.

- 실제 발생 수
- 정확 보고 수
- 미발견 수
- 오보고 수
- 평균 보고 시간
- 긴급 사건 해결 여부
- 최종 등급
- 서사 문서 또는 다음 날 힌트

# 6. CCTV 시스템

## 6.1 카메라 구성

각 CCTV는 하나의 횡스크롤 구역을 보여준다. 화면 너비보다 맵이 길어 좌우 탐색이 필요하다.

필수 속성:

- 카메라 ID
- 구역 ID
- 표시 이름
- 횡스크롤 경계
- 기준 상태 프로필
- 활성 이상현상 목록
- 사운드 버스 또는 공간 오디오 기준
- 현재 신호 상태
- 녹화 버퍼

## 6.2 조작

| 입력 | 기본 기능 |
|---|---|
| A/D 또는 마우스 가장자리 | CCTV 화면 좌우 이동 |
| 숫자 키 / 채널 버튼 | 카메라 전환 |
| 마우스 휠 | 제한적 확대·축소 |
| R | 최근 영상 재생 |
| Tab 또는 기록 버튼 | 기록 패널 열기 |
| Esc | 패널 닫기 / 메뉴 |

입력은 재매핑 가능하게 설계한다.

## 6.3 카메라 전환 규칙

- 정상 전환 시간: 0.15~0.35초
- 전환 시 짧은 아날로그 노이즈 사용 가능
- **주의:** 정상 채널 전환 노이즈는 보고 성공 노이즈보다 약하고 짧아야 한다.
- 카메라 전환 중 이상현상 타이머는 멈추지 않는다.
- 동일 프레임에서 여러 채널이 활성화되지 않는다.

## 6.4 정상 상태 스냅샷

각 구역은 근무 시작 시 기준 상태를 갖는다.

기준 상태는 다음을 포함한다.

- 오브젝트 활성 여부
- 위치, 회전, 스케일
- 스프라이트 또는 애니메이션 상태
- 문·조명·기계의 논리 상태
- 반복 환경음 상태
- 카메라 시간 표시 규칙

이상현상 정상화 시 개별 수작업 복구가 아니라 기준 상태로 복원한다.

## 6.5 최근 영상 재생

- 기본 길이: 8~10초
- 일차 사용 횟수 제한 또는 충전식
- 재생 중 세계 시간은 흐르는 방식을 권장
- 녹화 영상에서만 다른 모습을 보이는 특수 이상현상은 후반에 제한적으로 사용
- 재생 UI는 현재 실시간 영상과 명확하게 구분

# 7. 이상현상 시스템

## 7.1 이상현상 분류

| 분류 | 설명 | 예시 |
|---|---|---|
| 물체 변화 | 기존 오브젝트 상태가 달라짐 | 휠체어 이동, 의자 추가 |
| 인물 변화 | 인물 출현·중복·비정상 행동 | 걷지 않고 미끄러짐 |
| 공간 변화 | 구역 구조나 연결이 달라짐 | 끝나지 않는 복도 |
| 영상 변화 | CCTV 자체가 비정상 | 시간 불일치, 반복 재생 |
| 사운드 변화 | 시각 단서가 약한 음향 이상 | 지연된 발소리 |
| 연쇄 이상 | 미발견 시 다른 단계로 진행 | 휠체어 접근 |
| 긴급 사건 | 현장 해결이 필수 | 정전, 서버 장애 |

## 7.2 이상현상 생명주기

```text
Inactive
→ Scheduled
→ Warning
→ Active
→ Escalated (선택)
→ Normalizing → Resolved
또는
→ Missed → Consequence / NextStage
```

### Inactive
현재 일차에 존재하지만 아직 예약되지 않음.

### Scheduled
이벤트 스케줄러가 발생 시점을 예약한 상태.

### Warning
전조가 활성화된 상태. 전조는 공정성을 위한 단서이며 보고 대상이 아닐 수 있다.

### Active
명확한 변화가 발생해 보고 가능한 상태.

### Escalated
일정 시간 동안 발견되지 않아 더 명확하거나 위험한 상태로 변함.

### Normalizing
정확한 보고 직후 성공 노이즈와 기준 상태 복원 진행 중.

### Resolved
해당 일차에서 성공적으로 제거됨.

### Missed
활성 시간이 끝났으나 정확한 보고가 제출되지 않음.

## 7.3 발생 스케줄러 규칙

- 한 카메라에 판별이 어려운 이상현상 두 개를 동시에 배치하지 않는다.
- 동일 대상에 두 상태 변경을 중첩하지 않는다.
- 보고 패널이 열린 동안 타이머는 기본적으로 계속 흐른다. 접근성 모드에서는 느리게 할 수 있다.
- 현장 이동 중 일반 이상현상 스케줄러와 타이머는 정지한다.
- 성공 정상화 중 같은 구역에 새 이상현상을 생성하지 않는다.
- 미발견 2회 이후에는 제어실 접근 연출과 충돌하는 이벤트를 우선순위로 조정한다.
- 일차 종료 직전 보고 불가능한 짧은 이벤트를 예약하지 않는다.

## 7.4 전조 디자인 규칙

각 이상현상은 최소 하나의 전조를 가질 수 있다.

- 조명 1회 깜빡임
- 채널에 짧은 잡음
- 특정 방향의 발소리
- 문 아래 그림자
- 환경음 순간 정지
- 시계의 1초 정지

전조는 정답을 직접 알려주지 않지만 플레이어가 해당 채널을 다시 확인할 이유를 제공한다.

## 7.5 이상현상 공정성

- Active 상태는 최소 판별 가능 시간 동안 유지한다.
- 화면 밖에서 발생해 화면 밖에서 끝나는 이벤트는 금지한다.
- 지나치게 작은 픽셀 변화는 후반 또는 고난도 선택 옵션으로 제한한다.
- 색상만으로 판별하게 하지 않는다.
- 사운드형 이벤트는 시각적 접근성 표시를 제공한다.

# 8. 블록형 보고 시스템

## 8.1 기본 양식

```text
[구역] + [대상] + [이상 유형]
```

예시:

```text
[생활관 복도] [휠체어] [위치 변화]
```

## 8.2 구역 블록

현재 일차에 활성화된 카메라 구역만 노출한다.

예시:

- 생활관 복도
- 치료실
- 설비실
- 기록 보관실
- 격리 병동

구역 이름 옆에 CCTV 번호와 작은 미리보기를 제공할 수 있다.

## 8.3 대상 블록

구역을 먼저 선택하면 해당 구역에서 유효한 대상만 표시한다.

공통 대상:

- 문
- 조명
- 인물
- 공간
- 소리
- CCTV 영상
- 미등록 대상

구역 전용 대상 예시:

| 구역 | 대상 |
|---|---|
| 생활관 복도 | 휠체어, 의자, 액자, 비상구 |
| 치료실 | 침대, 커튼, 환자, 의료 장비 |
| 설비실 | 배전반, 발전기, 배관, 보안문 |

## 8.4 이상 유형 블록

초기 유형:

- 위치 변화
- 추가
- 소실
- 상태 변화
- 형태 변화
- 비정상 행동

후반 유형:

- 영상 반복
- 시간 불일치
- 소리 이상
- 공간 왜곡
- 중복 발생
- 기록 변조
- 관찰자 이상

## 8.5 사용하지 않는 블록

다음은 기본 보고서에 넣지 않는다.

- 관찰 유지
- 처리 방식
- 위험도
- 원인 추정
- 귀신, 괴물 같은 정체 분류

플레이어는 원인이 아니라 관찰된 사실만 기록한다.

## 8.6 판정

| 결과 | 조건 | 동작 |
|---|---|---|
| 정확 | 구역·대상·유형 일치 | 정상화 시작 |
| 불완전 | 구역·대상 일치, 유형 불일치 | 현상 유지, 재보고 제한 |
| 오인 | 구역 또는 대상 불일치 | 오보고 증가, 현상 유지 |
| 중복 | 이미 해결된 현상 | 반려, 큰 페널티 없음 |
| 비활성 | 해당 구역에 보고 가능한 현상 없음 | 오보고 처리 |

## 8.7 무차별 제출 방지

- 오보고 후 3~6초 재사용 대기시간
- 같은 조합 반복 제출 제한
- 제출 애니메이션으로 시간 비용 부여
- 일차 평가 정확도 감소
- 하드 모드에서 오보고 한도 사용 가능

기본 난이도에서는 오보고만으로 즉시 게임오버되지 않는다.

# 9. 정확한 보고와 정상화

## 9.1 성공 처리 흐름

```text
정확한 보고 제출
→ ReportAccepted 도메인 이벤트
→ 기록 UI 닫힘
→ 해당 CCTV 입력 잠금
→ 성공 노이즈 재생
→ 노이즈 중 기준 상태 복원
→ 비정상 사운드 제거
→ 신호 정상화
→ 입력 잠금 해제
→ 이상현상 Resolved
```

## 9.2 노이즈 연출 기준

- 전체 시간 권장: 0.9~1.6초
- 첫 0.2초: 프레임 고정 또는 수평 밀림
- 중간 0.4~0.8초: 강한 백색 잡음과 신호 손실
- 마지막 0.2~0.4초: 정상 영상 페이드인
- 성공 전용 사운드 모티프 포함

성공 노이즈는 다른 시스템 노이즈와 확실히 구분한다.

## 9.3 정상 배치 복원

노이즈가 화면을 가리는 동안 다음을 실행한다.

- 추가 오브젝트 비활성화
- 소실 오브젝트 재활성화
- 위치·회전·스케일 복원
- 스프라이트와 애니메이션 상태 복원
- 문·조명·기계 논리 상태 복원
- 이상 전용 오디오 중지
- 카메라 UI 시간·신호 상태 복원

## 9.4 잔여 연출

낮은 확률로 공포 연출용 흔적을 남길 수 있다.

- 복원된 휠체어 바퀴가 카메라를 향함
- 인물은 사라졌지만 발소리 한 번이 남음
- 액자의 표정이 미세하게 다름

잔여 연출은 새로운 이상현상도, 보고 대상도 아니다. 플레이어를 오답으로 유도할 수준이면 안 된다.

## 9.5 긴급 사건 예외

긴급 사건을 정확히 보고하면 정상화하지 않고 다음을 실행한다.

```text
EmergencyReportAccepted
→ 경고 UI
→ 원격 복구 불가 메시지
→ FieldObjective 생성
→ 플레이어 자리 이탈 허용
```

현장 해결이 완료된 뒤 CCTV 노이즈와 정상 복원을 실행한다.

# 10. 미발견과 접근 시스템

## 10.1 기본 실패 규칙

한 근무일에 미발견 이상현상 3개 누적 시 게임오버.

```text
MaxMissedPerDay = 3
```

수치는 난이도와 플레이 테스트 결과에 따라 조정 가능하나, 3을 기본 설계값으로 사용한다.

## 10.2 미발견 판정 시점

다음 조건을 모두 충족할 때 Missed 처리한다.

- 이상현상이 Active 또는 Escalated 상태
- 보고 가능 시간이 종료
- 정확한 보고가 없음
- 게임이 Monitoring 상태
- 일차 종료 처리 중이 아님

## 10.3 접근 단계

| 미발견 수 | 공포 상태 | 표현 |
|---:|---|---|
| 0 | 정상 | 제어실이 상대적으로 안전함 |
| 1 | 침투 시작 | 다른 CCTV에 흔적, 부재중 전화, 기록지 문장 |
| 2 | 제어실 접근 | 문 아래 그림자, 외부 발소리, 제어실 앞 카메라 |
| 3 | 침입 | 모든 채널 동기화, 문 잠금, 제어실 내부 영상, 게임오버 |

## 10.4 미발견 현상의 이동

미발견 후 원래 구역이 아무 흔적 없이 정상화되면 안 된다.

가능한 흔적:

- 바닥 자국
- 흔들리는 커튼
- 열린 문
- 끊어진 전선
- 화면 끝으로 사라지는 마지막 프레임
- 다음 카메라에서 동일 대상 재등장

## 10.5 연쇄 이상현상

예: 휠체어

```text
Stage 1: 생활관에서 위치 변화
Stage 2: 치료실에 추가
Stage 3: 인물이 앉음
Stage 4: 제어실 외부 카메라에 등장
Stage 5: 제어실 문 앞 바퀴 소리
```

어느 단계에서든 정확히 보고하면 성공 노이즈 후 최초 정상 위치로 복원하고 연쇄를 종료한다.

# 11. 긴급 현장 사건

## 11.1 목적

현장 사건은 플레이 리듬을 바꾸고, CCTV로 보던 공간을 직접 통과하게 만들어 감시 모드의 안전감을 붕괴시킨다.

## 11.2 발생 빈도

- 평균 일차당 1회
- 최대 2회
- 연속 발생 금지
- 첫 일차는 튜토리얼형 0~1회

## 11.3 현장 사건 흐름

```text
전조
→ CCTV 또는 시스템상 긴급 이상 확인
→ 정확한 보고 또는 자동 경보
→ 원격 복구 불가
→ 현장 목표 생성
→ 제어실에서 일어남
→ 횡스크롤 이동
→ 목표 상호작용
→ 귀환 연출
→ 제어실 복귀
→ CCTV 확인
→ 복구 노이즈와 정상화
```

## 11.4 현장 이동 중 시스템 규칙

- 일반 이상현상 타이머 정지
- 일반 이상현상 신규 발생 정지
- 긴급 사건 전용 이벤트만 실행
- 플레이어가 갈 수 있는 경로 제한
- 목표를 잃지 않도록 환경 표지와 업무 메모 제공
- 전투 없음
- 추격은 정식 버전 전체에서 1~2회 이하

## 11.5 대표 사건

### 정전

- 카메라 조명이 세 번 깜빡이고 암전
- 설비실 배전반 복구
- 복귀 중 뒤쪽 조명이 순서대로 꺼짐
- 제어실 도착 시 CCTV에 먼저 돌아온 복제 인물

### 카메라 오염

- 화면에 검은 액체
- 현장 렌즈는 깨끗함
- 카메라 아래 바닥에 액체
- 복귀 후 영상 속 플레이어가 현장에 남아 있음

### 서버 장애

- 모든 카메라가 과거 영상을 반복
- 서버실 모니터에 존재하지 않는 카메라 시점
- 재부팅 후 영상 속 플레이어만 움직이지 않음

### 격리실 개방

- 시스템은 개방 경고, CCTV는 닫힌 문
- 실제 현장에서는 열려 있음
- 벽에 “닫혀 있다고 기록하라”는 문장

## 11.6 현장 상호작용 범위

기본 상호작용은 다음으로 제한한다.

- 레버 당기기
- 버튼 누르기
- 퓨즈 교체
- 단말기 재부팅
- 잠금 장치 확인
- 전화 받기
- 짧은 문서 읽기

복잡한 인벤토리 퍼즐은 MVP에서 제외한다.

# 12. 횡스크롤 공포 연출 원칙

## 12.1 화면 끝

화면 좌우 끝은 항상 잠재적 위험 공간이다.

- 스크롤하면 함께 사라지는 얼굴
- 화면을 멈추면 가장자리에서 들어오는 손
- 항상 반대편 끝에 서 있는 인물
- 카메라 움직임을 따라오는 실루엣

## 12.2 지나온 방향

플레이어가 오른쪽으로 이동할 때 왼쪽에서 소리나 변화를 만든다.

- 방금 지나온 문 열림
- 조명 소등
- 같은 속도의 발소리
- 문패 변경
- 전경 뒤 실루엣

## 12.3 전경 가림

기둥, 커튼, 배관, 선반, 열린 문을 사용해 캐릭터를 잠시 가린다. 가려진 동안 캐릭터 옆에 다른 실루엣이 나타나거나, 나온 모습이 잠깐 달라질 수 있다.

## 12.4 추격 제한

추격은 관찰 공포의 보상 또는 클라이맥스다. 반복 콘텐츠로 사용하지 않는다.

괴물을 직접 보여주는 대신:

- 뒤쪽 조명 순차 소등
- 검은 공간 접근
- 빨라지는 발소리
- 차례로 열리는 문
- 전경을 앞질러 가는 그림자

# 14. 평가와 점수

## 14.1 평가 지표

- 발견률
- 보고 정확도
- 평균 대응 시간
- 오보고 횟수
- 긴급 사건 성공 여부
- 미발견 수
- 조사 도구 사용량

## 14.2 등급 초안

| 등급 | 기준 예시 |
|---|---|
| S | 모든 이상 발견, 오보고 0~1, 긴급 사건 성공 |
| A | 발견률 90% 이상, 생존 |
| B | 발견률 75% 이상, 생존 |
| C | 발견률 60% 이상, 생존 |
| D | 생존했으나 정확도 낮음 |
| F | 미발견 한도 초과 또는 필수 사건 실패 |

등급은 전투 능력치를 제공하지 않는다. 서사 문서, 엔딩 조건, 추가 기록 해금에 사용한다.

## 14.3 종료 시 공개 정보

기본 난이도에서는 놓친 이상현상의 정답을 즉시 전부 공개하지 않는다. 다음 중 일부만 제공한다.

- 놓친 구역
- 유형 범주
- 흐릿한 캡처
- 다음 일차 기록에 남은 흔적

접근성 또는 연습 모드에서는 전체 정답 공개가 가능하다.

# 20. 핵심 로직 의사코드

## 20.1 보고 판정

```csharp
ReportResult EvaluateReport(ReportSubmission submission)
{
    var candidates = anomalyService.GetReportableAnomalies(submission.AreaId);

    if (candidates.Count == 0)
        return ReportResult.FalseReport;

    var targetMatch = candidates.FirstOrDefault(a => a.TargetId == submission.TargetId);
    if (targetMatch == null)
        return ReportResult.FalseReport;

    if (targetMatch.ReportType != submission.ReportType)
        return ReportResult.IncompleteReport;

    return ReportResult.Accepted(targetMatch.InstanceId);
}
```

## 20.2 정확 보고 처리

```csharp
async Task HandleAcceptedReport(AnomalyInstance anomaly)
{
    anomaly.ChangeState(AnomalyState.Normalizing);
    eventBus.Publish(new ReportAccepted(anomaly.Id));

    cctvService.LockInput(anomaly.AreaId);
    await noiseEffect.PlaySuccessNoise(anomaly.AreaId);

    baselineService.RestoreArea(anomaly.AreaId);
    anomalyAudio.StopAll(anomaly.Id);

    anomaly.ChangeState(AnomalyState.Resolved);
    cctvService.UnlockInput(anomaly.AreaId);

    eventBus.Publish(new NormalizationCompleted(anomaly.Id));
}
```

실제 구현에서는 노이즈 중간 프레임에 복원을 실행해 전환이 보이지 않게 한다.

## 20.3 미발견 처리

```csharp
void HandleAnomalyTimeout(AnomalyInstance anomaly)
{
    if (gameFlow.CurrentMode != GameMode.Monitoring)
        return;

    anomaly.ChangeState(AnomalyState.Missed);
    daySession.IncrementMissed();
    eventBus.Publish(new AnomalyMissed(anomaly.Id));

    if (!string.IsNullOrEmpty(anomaly.Definition.NextStageId))
        anomalyService.ScheduleImmediate(anomaly.Definition.NextStageId);

    riskService.SetLevel(daySession.MissedCount);

    if (daySession.MissedCount >= daySession.MaxMissed)
        gameFlow.TriggerGameOver(GameOverReason.TooManyMissed);
}
```

## 20.4 현장 모드 진입

```csharp
async Task DispatchToField(EmergencyInstance emergency)
{
    scheduler.PauseNormalAnomalies();
    anomalyService.PauseAllNormalTimers();

    await gameFlow.TransitionTo(GameMode.FieldTraversal);
    fieldService.LoadObjective(emergency.FieldObjectiveId);
    eventBus.Publish(new FieldModeEntered(emergency.Id));
}
```

## 20.5 현장 복귀

```csharp
async Task ReturnFromField(EmergencyInstance emergency)
{
    await gameFlow.TransitionTo(GameMode.Monitoring);
    await normalizationService.NormalizeEmergencyArea(emergency.AreaId);

    anomalyService.ResumeAllNormalTimers();
    scheduler.ResumeNormalAnomalies();
    eventBus.Publish(new FieldModeExited(emergency.Id));
}
```

## 21.2 권장 저장 정책

MVP에서는 일차 시작과 종료 시 자동 저장한다. 감시 중 자유 저장은 구현 복잡도와 긴장 저하 때문에 제외한다.

크래시 복구가 필요하면 현재 일차의 결정적 랜덤 시드와 이벤트 인덱스를 저장한다.

## 21.3 버전 관리

저장 데이터에 `schemaVersion`을 포함하고 마이그레이션 함수를 둔다.

```json
{
  "schemaVersion": 1,
  "currentDay": 3,
```

# 27. 수용 기준

## 27.1 CCTV 기능

- 플레이어가 모든 활성 채널을 전환할 수 있다.
- 각 채널의 좌우 경계를 벗어나지 않는다.
- 채널 전환 후 이전 채널 상태가 유지된다.
- 정상 전환 노이즈와 성공 노이즈가 구분된다.

## 27.2 보고 기능

- 구역, 대상, 유형을 키보드·마우스로 선택할 수 있다.
- 정확 보고는 올바른 이상현상 인스턴스를 식별한다.
- 성공 후 해당 구역이 기준 상태로 복원된다.
- 오답은 현상을 제거하지 않는다.
- 같은 성공이 중복 처리되지 않는다.

## 27.3 미발견 기능

- Active 시간이 끝나면 Monitoring 상태에서만 미발견 처리된다.
- 미발견 횟수에 따라 위험 단계가 정확히 변경된다.
- 3회 시 게임오버 연출이 한 번만 실행된다.
- 현장 이동 중 미발견이 발생하지 않는다.

## 27.4 현장 사건

- 긴급 사건 보고 후 현장 목표가 생성된다.
- 목표 완료 전 일반 감시로 복귀할 수 없다.
- 완료 후 카메라 상태가 복구된다.
- 타이머 재개가 중복 호출되지 않는다.

3. 하드코딩 대신 설정 데이터와 인터페이스를 사용한다.

5. 상태 전환과 타이머 중복 실행을 방지한다.
6. 실패·취소·씬 전환 시 이벤트 구독을 정리한다.
7. 디버그 로그에 이상현상 ID, 상태, 구역, 시각을 포함한다.

10. 사용자에게 보이는 성공 노이즈는 `ReportAccepted` 또는 현장 해결 완료에서만 재생한다.

# 33. 최종 제품 기준 문장
