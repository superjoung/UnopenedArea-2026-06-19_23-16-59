# 《미기록 구역》 AI 활용 기술 문서 개정안

## 1. 3페이지 용어 설명: 심리스 타일

**심리스 타일(Seamless Tile)**은 동일한 이미지를 좌우 또는 상하로 반복 배치해도 이미지 경계가 끊겨 보이지 않도록 만든 반복형 텍스처이다.

《미기록 구역》에서는 긴 횡스크롤 맵의 벽·바닥을 공간마다 새로 그리는 대신, 반복 가능한 벽과 바닥의 기본 이미지를 만든 뒤 오염, 파손, 색감, 문, 커튼, 침대, 액자 등의 구획 요소를 추가해 서로 다른 공간처럼 구성하는 제작 방식에 해당한다.

이 용어는 AI 기술의 이름이 아니라 **배경 그래픽 제작 방식**이다. 비전공 평가자가 바로 이해할 수 있도록 문서에는 다음처럼 표기하는 것이 적절하다.

> 심리스 타일(경계가 보이지 않게 반복 배치할 수 있는 벽·바닥 이미지)

3페이지 표의 기존 문장은 다음과 같이 교체한다.

| 구분 | 기존 수작업 방식 | AI 파이프라인 적용 후 |
| --- | --- | --- |
| 배경 제작 공정 설계 | 반복 배치형 배경 제작 경험이 부족해 벽·바닥 연결과 작업 순서에서 시행착오 발생 | LLM에 횡스크롤 구조, 일정, 인원, 이상현상 가독성 조건을 입력해 심리스 타일 제작 순서와 리소스 우선순위를 빠르게 확정 |

- `[기획]` 보라색 `#6B5CA5`
- `[아트]` 주황색 `#B76A3C`
- `[개발]` 파란색 `#326B9A`

페이지 상단에는 네 색상의 작은 범례를 고정하고, 제목 왼쪽 세로선과 표의 첫 번째 열에만 포인트 색상을 사용한다. 본문 전체를 색칠하지 않아 인쇄 및 흑백 열람 가독성을 유지한다.

## 3. 4페이지: 아트 AI 파이프라인 레이아웃 수정

현재 파이프라인 박스의 하단과 다음 설명 문장이 거의 붙어 있어 서로 다른 정보 단위가 겹쳐 보인다.

- 파이프라인 박스 내부 상·하 여백: 10~12pt
- 박스와 앞 문단 사이: 8pt 이상
- 박스와 뒤 문단 사이: 14~16pt
- 파이프라인은 한 줄 화살표 대신 3단계 카드로 분리
- 각 카드에 담당 주체를 함께 표기

권장 파이프라인은 다음과 같다.

> **AI 탐색**  
> ChatGPT 이미지 시안 생성 · Gemini 제작 공정 비교  
> → **아티스트 제작**  
> 시안 선택 · 요소 분리 · 리터칭 · 색 보정  
> → **개발·검증**  
> Unity 배치 · Codex 데이터 교차 검사 · 플레이 테스트

박스 아래 설명 문안:

> AI는 비주얼 후보와 제작 공정의 탐색 속도를 높이는 데 사용했다. 최종 에셋의 선택, 분리, 리터칭과 색 보정은 아티스트가 수행했으며, 실제 CCTV 화면에서의 가독성과 게임 동작은 개발자가 Unity에서 검증했다.

## 4. 4페이지: 아트 활용 구현 상세 교체안

기존의 `A/B/C` 사례 제목을 **AI 활용 기술명**으로 먼저 제시하고, 각 사례를 `적용 방식 → 사람의 작업 → 효과` 순서로 통일한다.

| AI 활용 기술 | 적용 방식 | 사람의 판단·후처리 | 얻은 효과 |
| --- | --- | --- | --- |
| 생성형 이미지 기반 비주얼 탐색 | 공포, 폐쇄감, 노후 시설, CCTV 색감 조건을 입력해 배경과 키 비주얼 시안을 다수 생성 | 아티스트가 무드·색 팔레트·구도·오브젝트 밀도를 비교하고 최종 방향 선택 | 언어만으로 합의하기 어려운 분위기를 빠르게 시각화하고 초기 방향 결정 시간 단축 |
| LLM 기반 심리스 타일 공정 설계 | 횡스크롤 구조, 소수 인원, 짧은 일정, 이상현상 관찰 조건을 입력해 벽·바닥 반복 단위와 제작 우선순위 설계 | 아티스트가 실제 연결부, 오염·파손 변주와 공간별 구획 요소를 제작 | 공통 배경을 재사용하면서 여러 CCTV 공간의 차이를 확보하고 배경 제작량 절감 |
| 컨셉아트 요소 분리 및 프랍 에셋화 | 생성 시안에서 벽, 바닥, 문, 전화기, 침대, 휠체어, 액자 등 제작 대상을 식별하고 분리 기준 정리 | 아티스트가 투명 영역, 윤곽, 색상, 명암, 픽셀 밀도와 원근을 수작업 보정 | 정상·이상 상태를 교체할 수 있는 독립 프랍을 빠르게 확보하고 이상현상 제작에 재사용 |

`컨셉아트 파싱`은 개발 용어처럼 보일 수 있으므로 **컨셉아트 요소 분리 및 프랍 에셋화**로 바꾸는 편이 자연스럽다.

## 5. 프롬프트 설계 역량 강조 문안

### 제목

**제약 조건형 프롬프트 설계로 아이디어를 제작 가능한 명세로 전환**

### 본문

《미기록 구역》의 프롬프트는 단순히 아이디어를 요청하는 문장이 아니다. 게임의 시점, 해상도, 핵심 플레이 규칙, 1인 개발 범위, CCTV 축소 화면의 가독성, 제작 비용, 출력 형식과 검수 기준을 하나의 요청 안에 함께 설계했다. 이를 통해 AI의 답변을 일회성 아이디어가 아니라 기획 문서, 아트 제작 명세, 구현 데이터와 QA 체크리스트로 이어지는 반복 가능한 작업 단위로 변환했다.

프롬프트는 다음 다섯 요소로 구성했다.

1. **맥락:** 2D 횡스크롤 CCTV 감시형 공포게임
2. **제약:** 1인 개발, 고정 시점, 제한된 리소스, 작은 CCTV 화면
3. **평가 기준:** 가독성, 공정성, 중복 여부, 제작 난이도, 공포 강도
4. **출력 형식:** 규칙, Day, 콘텐츠 ID, Action, 에셋, 애니메이션 여부
5. **재검증:** 연관 탭·프리팹·데이터에 이전 값이 남았는지 재검색

### 역량 강조용 한 문장

> 생성형 AI에 정답을 요구한 것이 아니라, 프로젝트의 제약·평가 기준·출력 형식·검수 절차를 프롬프트에 설계해 아이디어를 실제 제작 가능한 사양으로 수렴시켰다.

### 실제 프롬프트 발전 사례

| 단계 | 프롬프트의 질문 | 고도화 결과 |
| --- | --- | --- |
| 아이디어 생성 | 새로운 이상현상 후보를 제안해 달라 | 위치 변화, 추가·소실, 형태 손상, 영상 이상 등 후보군 확장 |
| 비판·검토 | CCTV 가독성, 억울한 판정, 제작비 문제를 찾아 달라 | 작은 손동작 제거, 정적 스프라이트 우선, 미보고 공포와 보고 대상 분리 |
| 시스템 구조화 | 입력·조건·결과·예외로 정리해 달라 | CCTV 보고 루프와 현장이동 상호작용 규칙 확정 |
| 제작 명세화 | 디자이너가 바로 그릴 수 있는 형태로 바꿔 달라 | 정상·이상 차이, 이미지 수, 앵커, 애니메이션 여부 명시 |
| 데이터·QA | ID가 사용된 모든 데이터를 다시 확인해 달라 | 이상현상·Action·Schedule·프랍 명세 간 수정 누락 검수 |

### 한눈에 보이는 대표 사례: D2_A11

> **초기 아이디어:** 환자가 카메라를 향해 팔을 천천히 들어 올림  
> **AI 검토 조건:** CCTV 축소 화면 가독성, 애니메이션 비용, 기존 인물형 콘텐츠 중복  
> **사람의 판단:** 작은 손동작은 제한 시간 안에 발견하기 어렵다고 판단  
> **최종 결과:** 치료실 문 면적의 60~70%가 검은 구강과 큰 치아 형태로 변하는 정적 스프라이트 1장  
> **고도화 의미:** 아이디어 수를 늘리는 데 그치지 않고 플레이 공정성과 실제 제작 가능성을 함께 개선

## 7. 9페이지: MD 기반 통합 협업 프로세스 교체안

### 제목

**[통합·QA] AI 시대의 MD 기반 문맥 관리와 인수인계**

### 왜 MD로 정리했는가

생성형 AI 협업에서는 모델에게 전달되는 **문맥의 품질**이 결과의 일관성을 좌우한다. 채팅 기록만 남기면 최종 결정, 제외된 안, 변경 이유와 연관 데이터가 섞여 다음 작업자나 다른 AI가 같은 판단 기준을 재현하기 어렵다.

따라서 대화 결과를 Markdown 문서로 요약해 목표, 제약, 결정 사항, 변경 이유, 파일·콘텐츠 ID와 후속 검증 항목을 함께 기록했다. Markdown은 사람이 읽기 쉽고, Git에서 변경점을 비교할 수 있으며, 다른 AI 도구에도 구조화된 문맥으로 다시 전달할 수 있다. 이 문서는 단순 회의록이 아니라 **사람과 AI가 공유하는 작업 명세이자 결정 기록**으로 사용했다.

### 실제 개발 적용 흐름

1. 기획자가 목표, 게임 규칙, 제작 제약과 문제 사례를 AI에 전달한다.
2. AI가 대안과 위험 요소를 제안하고, 담당자가 채택·삭제와 우선순위를 결정한다.
3. 결정된 내용과 변경 이유를 PRD, 시나리오 바이블, 현장이동 정의서 등의 MD로 요약한다.
4. MD를 기준으로 아트 제작 명세, Google Sheets 콘텐츠 ID와 Unity 구현 항목을 갱신한다.
5. Codex가 같은 ID가 사용된 문서·데이터·프리팹 후보를 찾아 수정 범위와 QA 체크리스트를 제시한다.
6. 아티스트와 개발자가 원본 에셋·코드·데이터를 수정하고 Unity에서 실제 화면과 동작을 검증한다.
7. 최종 변경과 검증 결과를 Git diff, 날짜별 AI 활용 기록과 인수인계 문서에 남긴다.

### 실제 활용 사례

- CCTV 일반 이상현상에는 스토리 단서를 넣지 않고, 현장이동 메인 이벤트에서만 서사를 전달한다는 원칙을 MD에 고정했다.
- Day 1 배전반 복구, Day 2 훼손 기록 확대 관찰, Day 3 서버 기록 복구를 현장이동 공통 구조와 함께 인수인계했다.
- D2_A11 변경 시 이상현상명뿐 아니라 보고 대상, Action, 스프라이트, 애니메이션 여부, Day Schedule과 디자이너 프랍 명세까지 같은 ID로 재검색했다.
- AI가 제안한 내용과 사람이 최종 확정한 내용을 분리해, 자동 생성 결과가 곧 완료 상태로 오인되지 않도록 했다.

### 평가자에게 전달할 핵심 문장

> AI와의 대화를 일회성 채팅으로 소비하지 않고, 결정 이유와 제작 제약을 MD 명세로 축적해 기획·아트·개발이 동일한 문맥을 재사용할 수 있는 협업 체계를 만들었다.

## 8. 최종 편집 원칙

- 한 페이지에는 핵심 메시지를 최대 3개만 둔다.
- 모든 사례는 `AI 활용 기술 → 적용 방식 → 사람의 판단 → 효과` 순서를 따른다.
- 각 표에는 담당 파트를 명시해 “누가 AI를 사용했고 누가 확정했는지”를 구분한다.
- 긴 설명 대신 D2_A11처럼 초기안과 최종안을 비교하는 대표 사례를 강조한다.
- 프롬프트 원문은 전부 싣지 않고, 제약·평가 기준·출력 형식이 보이는 핵심 구절만 강조한다.
- `심리스 타일`, `파싱`, `ScriptableObject` 등 전문 용어는 첫 등장에 한글 설명을 병기한다.
- 수치 성과는 측정 근거가 있을 때만 사용하고, 추산인 경우 “팀 내부 추산”과 측정 범위를 함께 표기한다.
